# Порядок разработки NES

Правила совместной работы над конфигурацией `НЭС_ЗУП` и расширением `NES` в EDT и git.
Правила по содержанию доработок (что в конфигурацию, что в расширение) - в `CLAUDE.md`.

## Ветки

| Ветка | Назначение | Кто пишет |
|---|---|---|
| `master` | то, что стоит в рабочей базе | только слияние из `dev` после тестирования |
| `dev` | общая ветка тестирования | только через PR |
| `task/<номер>-<кратко>` | одна задача | автор задачи |
| `update/<версия>` | обновление типовой ЗУП | один ответственный |

- Ветка задачи создается от свежего `dev`. Одна задача - одна ветка - один PR.
- `dev` вливается в `master` по результатам тестирования, это делает один ответственный.
- На GitHub для `master` и `dev` включена защита: изменения только через PR и минимум одно одобрение
  (Settings - Branches - Branch protection rules).

## Ежедневный цикл

1. **Начало дня.** Переключиться на `dev`, Pull. Перенести `dev` в свою ветку задачи (Merge).
   Чем реже это делать, тем тяжелее конфликты.
2. **Работа - только в EDT.** Если что-то сделано в Конфигураторе, сразу импортировать в EDT,
   иначе следующая выгрузка из EDT затрет правку.
3. **Перед коммитом:**
   - в Configuration Problems нет новых ошибок;
   - в окне коммита просмотреть список файлов и отметить только свои. Сотни `.svg` или модулей,
     которые не правились, - это ложные изменения, их не коммитить;
   - не нажимать "Отклонить изменения", если нет уверенности, что именно отбрасывается.
     Безопасный вариант - "Спрятать" (Stash).
4. **Push в конце дня**, даже если задача не закончена. Коммиты, которые есть только на одной
   машине, теряются.
5. **PR в `dev`.** Коллега просматривает изменения, после одобрения - слияние.

## Информационные базы

- У каждого разработчика своя база. Общую базу для разработки не использовать: обновление
  конфигурации одним сбивает работу остальных.
- Тестовая база одна, обновляется из `dev`, отвечает за нее один человек.
- Рабочая база обновляется только из `master`.
- Конфигурация и расширение обновляются в базе вместе, в одном запуске.
- Базы, пароли, `.dt`, `.cf`, `.cfe` в git не кладутся.

## Где конфликтуют чаще всего

| Место | Что делать |
|---|---|
| `Configuration.mdo` (списки объектов) | при конфликте оставлять обе строки - свою и чужую |
| `Rights.rights` ролей, большие типовые общие модули | мелкие PR, частый перенос `dev` в свою ветку |
| Формы (`Form.form`) | автоматически сливаются плохо. Одну форму одновременно правит один человек, это фиксируется в трекере задач |
| Номер версии расширения | поднимается только при выпуске (`dev` в `master`), не в каждой задаче |
| Обновление типовой ЗУП | один ответственный в ветке `update/<версия>`, затем PR в `dev`. На это время остальные не правят основную конфигурацию |

## ИИ-агенты

Агенты (Cursor, Claude и другие) работают по тем же правилам: своя ветка на задачу, PR в `dev`,
слияние только после проверки человеком в EDT.
